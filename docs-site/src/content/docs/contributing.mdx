Bug reports, feature requests, documentation, code - all welcome. This page is the short version. The
repository's [CONTRIBUTING.md](https://github.com/x-rous/actual-bench/blob/main/CONTRIBUTING.md) is
the long one.

## Ways to contribute

- Report a **bug**.
- Suggest a **feature**.
- Fix or improve **documentation**.
- Contribute **screenshots** that match the current UI.
- Contribute **code**.
- Help by **testing** changes.

## Report a bug or suggest a feature

Open an issue on [GitHub](https://github.com/x-rous/actual-bench/issues) with the right template.
Search first - someone may have got there already. For a bug: version, browser, OS, connection mode,
the exact steps, and what you expected instead.
[Troubleshooting](../help/troubleshooting/#reporting-a-bug) lists the rest.

## Set up the project

```bash
git clone https://github.com/x-rous/actual-bench.git
cd actual-bench
npm install
npm run dev
```

Use Node.js `24.22.3` or later (the version in `.nvmrc`). Testing HTTP API Server mode properly needs a running `actual-http-api` - point
it at a test budget, not your own.

## Branch and PR model

Work on short-lived branches that target `main`:

| Type | Branch prefix |
|---|---|
| Feature | `feat/*` |
| Bug fix | `fix/*` |
| Refactor | `refactor/*` |
| Docs | `docs/*` |

Every pull request targets `main`. Keep one focused on one thing. Title it the way a user would
describe it, and attach screenshots for anything visual. Ships a feature? Update `FEATURES.md`.
Changes what a user sees? Update these docs in the same PR.

## Documentation contributions

The docs are their own Astro Starlight project, under `docs-site/`:

```bash
cd docs-site
npm install
npm run dev      # http://localhost:4321/actual-bench
npm run build
```

When writing docs:

- The **running app** is the source of truth. Use its exact labels.
- Write for someone who uses Actual every day and has never opened Bench. Plain words, short
  sentences, no internal terms (schema versions, query keys, retry semantics, layout details).
- Open every feature page the same way: two or three sentences on what it is for and why you would
  use it, then where to find it and whether it changes Actual, in one sentence. Then a picture, then
  the shortest path to a first result.
- Say each thing once. What changes Actual and when lives on **Work safely**; the shared editing
  model lives on **Editing, review and save**. Link to them instead of repeating them.
- Describe what Bench does with your own data. Avoid "Actual can't, Bench can" comparisons.
- Put deep reference (formulas, edge cases, matching constants) at the end, or in a collapsed
  `<details>` block, so the page stays approachable without losing anything.
- Use a table or list when readers compare choices. Keep paragraphs to one idea.
- One task, one page. A smaller workflow is a section, not a new page.
- Put images under `docs-site/src/assets/screenshots/` and reference them relatively.
- No real secrets, credentials, private hostnames or personal budget data. Ever.
- Keep links **relative** (`../accounts/`). A link starting with `/` skips the site's base path and
  breaks on the published site.

Every page has an **Edit** link that takes you straight to its source file on GitHub.

## Validate before submitting

From the repository root:

```bash
npm run lint      # 0 errors
npx tsc --noEmit  # 0 errors
npm test          # passes
npm run build     # succeeds
```

Documentation-only change? Run the docs build too: `npm --prefix docs-site run build`. CI checks it on
every pull request.

## Security issues

Found a vulnerability? Do not put the exploit in a public issue. The repository's security policy has
the private channel.
