This page picks up after [Installation](../../getting-started/installation/), for running Actual
Bench properly: on HTTPS, with its data kept safe, and reachable from wherever you use it. A typical
setup is one container, one persistent `/data` volume, and a reverse proxy in front.

## How it fits together

- **Direct mode:** the browser talks to your Actual Server itself, running Actual's engine in a
  background worker. Bench serves the app; your budget data does not pass through it.
- **HTTP API mode:** the browser only talks to Bench, which forwards requests to `actual-http-api`
  from the server. The browser never sees that address.

Either way, Bench keeps its own small database under `/data`.

Running Bench on one computer for yourself, without Docker? The [desktop app](../desktop-app/) for
Windows and macOS is the whole of Bench in one installable app, and works with the Actual desktop
app's own server.

## Pin an image

Images are published for `linux/amd64` and `linux/arm64`:

- `xrous/actual-bench:latest` - the current stable release.
- `xrous/actual-bench:<version>` (for example `:1.4.0`) - one release, unchanging.
- `xrous/actual-bench:edge` - rebuilt on every merge, for testing only.

Pin a version in production, so upgrades happen when you decide, not whenever the container
restarts.

```yaml
services:
  actual-bench:
    image: xrous/actual-bench:1.4.0   # pin a version in production
    container_name: actual-bench
    ports:
      - "3000:3000"
    volumes:
      - actual-bench-data:/data
    restart: unless-stopped

volumes:
  actual-bench-data:
```

[Configuration](../configuration/) lists every environment variable. None are required.

## Hosted platforms

These run the same image with a platform's own tooling.

- **Fly.io:** follow [Deploy on Fly.io](../fly-io/), a step-by-step guide that needs no prior
  experience.
- **PikaPods:** available once the official listing is approved, with one port (3000) and one
  volume (`/data`).

## Network

Two different paths matter, and mixing them up is the most common deployment mistake:

- **Direct mode:** the user's **browser** must reach the Actual Server.
- **HTTP API mode:** the Actual Bench **container** must reach `actual-http-api`.

### Direct mode

- The browser must be able to open your Actual Server's address.
- Scheduled runs on Direct budgets (backups, bank sync, sync flows) open the budget on the Bench
  server, so **the Bench server** must reach the Actual Server too.
- The Actual Server must allow the browser's requests (CORS), or sit behind the same reverse proxy as
  Bench so the two share one origin.
- Serve both over **HTTPS**. Browsers only run Direct mode's engine on a secure page (HTTPS, or
  `localhost`), and Direct mode sends your server password from the browser, so plain `http://`
  would also put it on the wire. Bench sets the cross-origin isolation headers Direct mode needs on
  its own pages. Without a reverse proxy, set `ACTUAL_BENCH_HTTPS=true` and Bench serves HTTPS itself
  with a self-signed certificate: see [Built-in HTTPS](../configuration/#built-in-https).

If an environment cannot support Direct mode, there is nothing to switch off: Bench says so clearly
when someone connects, and they can use HTTP API mode instead.

### HTTP API mode

- The Bench container must reach the `actual-http-api` address. The browser never uses it.
- If both run in Docker, put them on one network and use the API's service name.

:::caution[`localhost` inside a container is the container itself]
Point Bench at `localhost` and it will call itself. Use the API's service name on a shared Docker
network, or an address that resolves from inside the container.
:::

`fetch failed` or `502 Bad Gateway` in HTTP API mode is almost always container-to-container
networking.

## Reverse proxy and HTTPS

For a home LAN with no proxy, [built-in HTTPS](../configuration/#built-in-https) is enough. For
anything reachable from outside, or to use a trusted certificate without warnings, put a reverse proxy
(Caddy, Traefik, Nginx) in front and terminate HTTPS there, with `ACTUAL_BENCH_HTTPS` left off:

- Forward the original **host** and **protocol** headers.
- Serving the Actual Server on the same scheme, hostname and port as Bench (for example under a path
  such as `/actual`, routed by the proxy) makes it same-origin, which solves Direct mode's CORS needs
  without opening CORS up. On its own hostname, such as `actual.example.com`, it is a different
  origin even behind the same proxy, and still needs CORS.
- Once the hostname is HTTPS-only, enable **HSTS** at the proxy. Bench does not send it itself,
  because it also runs over plain HTTP on a LAN.
- Don't strip Bench's own security headers, and don't add a second `Content-Security-Policy` at the
  proxy: it would block the app's scripts. CDN features that inject scripts into pages (such as
  Cloudflare Rocket Loader) need switching off for this hostname.

## Access

Bench asks for a password before anything else (see [Sign-in](../configuration/#sign-in)). The
first visitor to a new install sets it, so open Bench right after deploying it, or set
`ACTUAL_BENCH_PASSWORD` in advance.

- On the internet, an extra layer in front (your identity provider, or a VPN such as Tailscale) is
  still worth having. If that layer already controls access, you can turn Bench's sign-in off with
  `ACTUAL_BENCH_AUTH=none`.
- When a proxy is the way in, don't also publish port `3000` on the host, or anyone could go around
  the proxy.

Bench refuses requests that change data when they come from another website, so a page you visit
cannot act on a Bench it can reach through your browser, even on your LAN. It also refuses to
connect to cloud metadata addresses, and stops (showing the address) rather than follow a redirect
to a different server or from `https` to `http`.

## Keep it safe

- **Persist and back up `/data`.** It holds Bench's database and the generated vault key
  (`secrets/vault.key`). Lock down its permissions.
- If you set `ACTUAL_BENCH_VAULT_KEY`, keep it in your platform's secret manager, out of the image
  and out of git.
- Don't expose `actual-http-api` or the Actual Server more widely than you need to.
- Redact secrets before sharing logs.

## One instance

The scheduler that runs automations lives inside the Bench server and ticks about once a minute. Run
**one** instance: two containers on one database would run every automation twice.

## Checklist

- [ ] A pinned `:<version>` image.
- [ ] `/data` mounted, writable and backed up.
- [ ] A password set (on first visit, or with `ACTUAL_BENCH_PASSWORD`), and port `3000` not published
      beside the proxy.
- [ ] HTTPS at the proxy, with host and protocol headers forwarded.
- [ ] Direct mode: the browser (and, for automations, the Bench server) can reach the Actual Server.
- [ ] HTTP API mode: the Bench container can reach `actual-http-api`.
- [ ] [App Health](../app-health/) shows **Writable** `Yes`, a schema version, and the credential vault
      ready.
